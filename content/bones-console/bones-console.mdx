# Bones Command-Line Interface

This document explains the Bones command-line interface included with WP Bones Boilerplate. It provides helpful commands for plugin development. You can start by running `php bones` and change the plugin namespace using `php bones rename "My First WP Bones Plugin"`. It highlights the importance of using double quotes for arguments with spaces on Windows. The document also covers the `deploy` command to create a folder for submitting your plugin to the WordPress.org repository.

## Overview

Bones is also the name of the command-line interface included with all our [WP Bones Boilerplate](/docs/getting-started/boilerplate-templates). It provides a number of helpful commands for your use while developing your plugin. You will use the Bones command-line interface to start your development. First of all, try the command-line console by running:

```ansi
[38;5;76m>[0m php bones
```
<PHPBonesCommand my={32}  />

Then, you can change the plugin namespace from `WPKirk` to `My First WP Bones Plugin`, for example:

```sh copy
php bones rename "My First WP Bones Plugin"
```
<Callout type="important" emoji={<IconBrandWindows />}>
__On Windows__, the command line treats single quotes differently than double quotes. To ensure compatibility, always use double quotes for arguments containing spaces.
</Callout>

<Callout type="info">
As you can see from the above command, the plugin name is enclosed in double quotes. This is because the plugin name contains spaces. If the plugin name does not contain spaces, you can omit the double quotes. Moreover, the plugin name is the first argument and you can skip the second argument if you want to use the namespace generated by the plugin name.
</Callout>

Great! You are quite ready to start developing.

## Common Commands

<Callout type="info">
Since `v2.0.10` every command exits with a non-zero status when it fails, and with `1` when you answer "no" to a confirmation or nothing answers it, as in a script; errors are written to stderr. To confirm from a script, pipe the answer: `echo y | php bones version 1.2.0`.
</Callout>

### `deploy`

When your plugin is ready, you can use the `deploy` bones command in order to create a new folder useful to submit your plugin to the wordpress.org repository.

```sh copy
php bones deploy your-path/mydeploy
```

Remember that you can ask for help by using:

```sh copy
php bones deploy --help
```

```sh copy
Usage:
  deploy <path> <options>

Arguments:
  path		The complete path of deploy.

Options:
  --wp				You are going to release this plugin in the WordPress.org public repository.
  --create-zip			Creates an installable plugin zip file instead of deploying in a directory.
  --pkgm=<package-manager>	Forces the deployment to use the specified package manager, Eg. npm, yarn, ...
  --no-build			Forces the deployment to skip the build process.
  --keep-ignored		Packages files that git ignores as well (they are left out by default).
  --keep-dev			Packages Composer's require-dev packages as well (they are removed by default).
  --force			Replaces a destination folder that is neither empty nor a previous deploy of this plugin.
```

#### Where the deploy goes

The deploy deletes the destination folder and fills it again, so since `v2.0.10` it checks the folder first, before anything is built:

- the plugin itself, any folder that contains it (`..`, your home) and any folder inside it are **always refused**, `--force` or not;
- an existing folder is replaced only when it is empty or holds a previous deploy of this plugin, that is its main file with the same `Plugin Name`;
- anything else is left alone, and the deploy stops and says so. Pass `--force` if that folder really is yours to replace.

<Callout type="warning">
Up to `v2.0.9` an existing destination was deleted after a five-second pause and nothing else: `php bones deploy ..` removed every plugin beside yours and the plugin itself, and `php bones deploy build` copied the plugin into `build/build/build/…` until the path was too long.
</Callout>

#### What the deploy leaves out

Since `v2.0.6` the deploy asks your plugin's own git repository what it ignores and skips it, listing every path it left out. That is how a local `POST.md` stops travelling to WordPress.org: the file is invisible to `git status`, so nothing else in a release points at it.

Three directories are never consulted, because your repository's ignore rules do not describe them: `vendor/` is composer's output and your plugin needs it at runtime, `public/` holds what the build has just produced, and `storage/` is the runtime directory. Most plugins gitignore all three.

Use `--keep-ignored` when an ignored file really does belong in the package. If the plugin is not a git repository, nothing is filtered.

#### Composer dev packages

The deploy copies `vendor/` as it is on disk, and a working copy normally has the `require-dev` tree installed — PHPUnit, Brain Monkey and the like. Up to `v2.0.6` all of it went into the package, WordPress.org included, unless your `deploy.php` ran `composer install --no-dev` itself.

Since `v2.0.7`, when `vendor/composer/installed.json` lists dev packages, the deploy runs `composer install --no-dev --no-scripts --no-plugins --optimize-autoloader` **in the deployed copy**, against your plugin's `composer.lock`. Your working copy is never touched, and `--no-scripts` keeps `post-autoload-dump` from renaming namespaces a second time. Without a `composer.lock`, or without Composer on the machine, the deploy stops rather than ship the dev packages. Pass `--keep-dev` to package them anyway.

<Callout type="warning">
Also since `v2.0.6`, a production build that fails **stops the deploy**. Before that the build ran through `shell_exec()`, which discards the exit status, so a broken build printed `✅ Build completed` and the command went on to package whatever was already in `public/`.
</Callout>
The `--wp` option will create a deploy folder with the necessary files to submit your plugin to the WordPress repository. For further information, see [here](../getting-started/before-submit-to-wordpress-repository).

#### `--wp`

<Callout emoji={<IconBrandWordpress />}>
Starting from WP Bones `v1.5.0` we added a new option `--wp` to deploy the plugin to the WordPress repository. This option will create a deploy folder with the necessary files to submit your plugin to the WordPress repository. For further information, see [here](../getting-started/before-submit-to-wordpress-repository).
</Callout>

In the `mydeploy` folder, you will find only the necessary files to run your plugin.
Without the `--wp` option the developer's `resources/assets` folder will be removed.

### Customize Deploy

Of course, you may customize the deployment process by editing the `deploy.php` file. In this file, you can add your own commands to run before and after the deployment. You will also find some actions and filters to customize the deployment process.

For example, you can add any custom command to run before the deployment by using:

```php copy
/**
* Fired when the deploy command is started
*
* @param object $console Instance of WPBones Console
* @param string $path Destination path
*/
add_action('wpbones_console_deploy_start', function ($console, $path) {
    // Do something
}, 10, 2);
```

Or change the list of skipped files by using:

```php copy
/**
* Filter the list of the folder to skip for the deploy version
*
* @param array $folders List of folders to skip
* @return array List of folders to skip
*/
add_filter('wpbones_console_deploy_skip_folders', function ($folders) {
    return $folders;
});
```

→ See more about [Actions & Filters](../wordpress-integration/actions-and-filters).

### `require`

The `require` command is used to install third-party packages. You can use the `require` command by running:

```sh copy
php bones require <PackageName>
```

Under the hood the `require` command uses the `composer require` command. But it also renames the package name in the `composer.json` file.

We recommend using this command instead of `composer require` because by doing so, an automatic renaming will be performed.

### `tinker`

The `tinker` command is used to open an interactive shell. You can use the `tinker` command by running:

```sh copy
php bones tinker
```

Now you can run any PHP code

```sh copy
>>> echo "Hello"
Hello
```

You can also use any WordPress function

```sh copy
>>> echo get_bloginfo('version');
6.6.2
```

A value you `return` is printed, variables live until the session ends, and an error is shown without closing the shell. The session ends with `exit`, with Ctrl-D, or when piped input runs out. Before `v2.0.10` errors printed nothing, and piped input without a final `exit` never ended.

### `version`

The `version` command is used to version your plugin. You can use the `version` command by running:

```sh copy
php bones version 1.0.0
```

The above command updates the version everywhere your plugin declares it: the main plugin file, `readme.txt`, and — since `v2.0.6` — `package.json` and the two root entries of `package-lock.json`. Each file it changes is listed:

```sh
→ readme.txt > 1.4.0 (Stable tag: 1.4.0)
→ wp-kirk.php  > 1.4.0 ( * Version: 1.4.0)
→ package.json > 1.4.0 (1 entry)
→ package-lock.json > 1.4.0 (2 entries)
✅ Version updated to 1.4.0
```

Your dependency tree is not touched: everything from the first `"node_modules/"` key of the lockfile onwards is left exactly as npm wrote it.

<Callout type="warning">
A v1 lockfile, written by npm 5 or 6, has no `"node_modules/"` key. Up to `v2.0.8` the command therefore also rewrote the first dependency's version in it; since `v2.0.9` only the root entry changes, and the output reads `(1 entry)`.
</Callout>

<Callout>
Despite PHP Bones supporting semantic versioning, we suggest you use the same version in the `readme.txt` file and in the main plugin file. In short, avoid using the `v` prefix in the version number.
</Callout>

You can see the help by using:

```sh copy
php bones version --help
```

```sh copy
readme.txt > 1.4.0 (Stable tag: 1.4.0)
wp-kirk.php  > 1.4.0 ( * Version: 1.4.0)

Usage:
  version [plugin version]

Arguments:
  [plugin version]		    The version of plugin. Examples: '2.0',  'v1.2',  '1.2.0-rc.40', 'v1-beta.4'
  [--major]			        Increment the <major>.y.z of plugin.
  [--minor]			        Increment the x.<minor>.z of plugin.
  [--patch]			        Increment the x.y.<patch> of plugin.
  [--pre-patch] <prefix>	Increment the x.y.<patch>-<prefix>.<i> of plugin.
  [--pre-minor] <prefix>	Increment the x.<minor>.z-<prefix>.<i> of plugin.
  [--pre-major] <prefix>	Increment the <major>.y.z-<prefix>.<i> of plugin.
```

The `php bones version` command can handle the version starting from the current version of the plugin. You can use the following options:

#### `--major`

Increments the major version number. For example, if the current version is `1.0.0`, the new version will be `2.0.0`.

#### `--minor`

Increment the minor version number. For example, if the current version is `1.0.0`, the new version will be `1.1.0`.

#### `--patch`

Increment the patch version number. For example, if the current version is `1.0.0`, the new version will be `1.0.1`.

You can also use the `--pre-patch`, `--pre-minor`, and `--pre-major` options to increment the version with a prefix. For example, if the current version is `1.0.0`, the new version will be `1.0.1-rc.1`.

The default prefix is `rc`. But you can change it by using:

```sh copy
php bones version 1.0.0 --pre-patch beta
```

The above command will update the plugin version to `1.0.1-beta.1`.

### `migrate:to-v2`

New in **v2.0**. Converts a v1.x gulp-based plugin to the v2 webpack infrastructure.

```sh copy
php bones migrate:to-v2
```

The command removes `gulpfile.js` and `package-lock.json`, creates
`webpack.config.js`, `tsconfig.json`, `.prettierrc`, and `jest.config.js`
from the framework stubs, rewrites `package.json` scripts to the unified
`dev/build/test/format/lint` block, drops gulp-era devDependencies, and
installs the v2 set (`@wordpress/scripts ^31`, `typescript`, `glob`,
`less-loader`, `webpack-remove-empty-scripts`, `@types/react*`). Your
`resources/assets/` tree is left untouched — your code is preserved.

After migration, run:

```sh copy
yarn install && yarn build
```

<Callout type="warning">
Commit your work first. The migration rewrites several files. You can
always `git restore` if anything looks off.
</Callout>

See the full [Migrating to v2](/docs/migrating-to-v2) guide for the end-to-end diff.

## Creators

The Bones command console provides a set of commands to create some base classes. For example, you can create a Custom Post Type by using:

```sh copy
php bones make:cpt MyCustomPostTypeClass
```

Every creator that writes a PHP class takes a class name or `Folder/ClassName` (`make:console` takes a class name only, since the kernel loads `plugin/Console/Commands/*.php`), and the namespace follows the folder: `php bones make:controller Shop/Cart` writes `plugin/Http/Controllers/Shop/Cart.php` in `…\Http\Controllers\Shop`. `make:app`, below, takes an app name instead.

<Callout type="info">
Since `v2.0.10` the class creators never overwrite a file that already exists: they stop and leave it as it is. Pass `--force` to overwrite it. A name that is not a PHP class name, or that climbs out of the folder with `..`, is refused. `make:app` refuses an existing app, `--force` or not.
</Callout>

### `make:app`

New in **v2.0**. Scaffolds a new React/TypeScript app under
`resources/assets/apps/`. Webpack auto-discovers the new entry — no
`package.json` edits needed.

```sh copy
php bones make:app dashboard
# → resources/assets/apps/dashboard/index.tsx (folder-based)

php bones make:app widget --flat
# → resources/assets/apps/widget.tsx (single-file)
```

Each generated app is a React 18 component using `createRoot` from
`@wordpress/element` and `__` from `@wordpress/i18n`, mounted on a
`#<name>-root` div. The Text Domain is auto-resolved from your plugin
header.

After scaffolding, add the mount div to your view and enqueue the bundle
from your controller:

```php copy
<div id="dashboard-root"></div>
```

```php copy
return WPKirk()
  ->view('dashboard.index')
  ->withAdminAppsScript('dashboard');
```

<Callout type="warning">
The command refuses names that collide with WordPress core script handles
(`dashboard`, `post`, `common`, `jquery`, `wp-element`, etc.). If the
handle is already registered by core, `wp_enqueue_script` silently drops
your bundle and the app never mounts. Pick a distinctive name like
`admin-ui`, `analytics`, or a plugin-specific prefix.
</Callout>
